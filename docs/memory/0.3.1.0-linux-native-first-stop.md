# 0.3.1.0 — the first stop of the native self-build is `byte`, not aggregates

**Lane**: `remodel/0.3.1.0-linux-native`, based on upstream `38a8875` (the org's `.31` tip).
**Goal of the lane** (owner's platform-sequenced plan): the Linux leg generates NATIVE. Version
formula unchanged, bump stays incremental; macOS/Windows/wasm keep the C route; C lives until
0.3.1.4. Done = the fixpoint holds in native on the Linux leg.

## Why Linux is sequenced first — breadth, not ease (owner's ruling, 2026-07-28)

This is **not** because Linux is easier. The four Linux legs (`x86_64-glibc`, `x86_64-musl`,
`arm64-glibc`, `arm64-musl`) measure the **same shared lowering** (`src/lir/lower.tks`) across four
platform combinations — the greatest breadth per unit of effort.

**What is shared and what is not:** the LIR lowering is shared across all platforms. Only byte
emission is per-platform — instruction selection (`isel x86-64`, `isel arm64`, `isel wasm`), object
writers (ELF, PE, Mach-O), and platform-specific variants like `B1-fp` (floats on x86-64) and
`B1-args` (stack arguments on Windows). **Therefore degraus 1 through 6 already benefit macOS,
Windows, and wasm**, untouched: the `byte` machine class, variant cases by keyword, short-circuit
`&&`/`||`, aggregate push, fat `match`, and the variant wrapper — all are fixes in shared code that
any platform reaching here will receive.

**What remains for the other platforms — and it can be substantial:** macOS and Windows have their
own emission work. The owner said it plainly: *"they can have a lot of things that won't work"*.
That work is the entire emission half: instruction selection for x86-64 (including `B1-fp` for
floats), `B1-args` (Windows stack passing), the PE `TimeDateStamp` (which broke Windows fixpoint
in 0.3.0.31), and the object writers. All orthogonal to the shared lowering.

## The measuring loop — 66 seconds, no network

```sh
sh scripts/build_gen1_from_c.sh bootstrap/teko.c src .gen1   # 26s — the trampoline
TEKO_BACKEND=native ./.gen1/teko . -o .gen2-native --no-verify --release   # 40s — to the stop
```

## What it says today

```
teko: .: native backend N1: a push whose element is an AGGREGATE
(`struct`/`class`/variant/optional/closure) needs slice elements held BY VALUE — this backend's
aggregate value is the address of a per-INSTRUCTION frame slot, so a push in a loop would store
the same address every iteration (N2)  [in `teko::backend::emit_u32_le`]
```

## Why that message is misdiagnosing

`emit_u32_le` pushes **bytes** into a `[]byte`. Nothing about it is an aggregate. Reduced to
twelve lines and narrowed by element type:

| element | verdict |
|---|---|
| `i32` | compiles |
| `u8` | compiles |
| **`byte`** | **the "AGGREGATE" stop** |
| `f64` | a different, already-named stop: `isel x86-64: B1-fp` (the float family) |

The cause is in the type model, and it is two missing match arms, not a redesign:

`src/checker/type.tks:126`
```teko
pub type Type = variant Prim | Byte | Char | Str | Slice | Optional | Named | Variant | Func | Error | Void | Ptr | Uptr | Reference | Null
```

`byte` is its **own variant member**, a sibling of `Prim` — `PrimKind` (`type.tks:11`) has no
`Byte` (`typer.tks:1792` records the intent as "byte AS u8"). Two functions in `src/lir/lower.tks`
enumerate `Prim` and fall through on everything else:

- `is_register_value_type` (`lower.tks:5325`) — `Prim => true`, enum-`Named => true`, `_ => false`.
  A `byte` lands in `_`, so the push guard calls it an aggregate and raises the stop above.
- `ltype_of` (`lower.tks:270`) — `Prim`, `Void`, `Named`, then `_ => LType::Ptr`. A `byte` is
  therefore given the **address-shaped, 8-byte** machine class instead of a one-octet integer.

The second is the more serious of the two: it is not a guard, it is the machine class every
downstream consumer reads. A `[]byte` element stride, an index load, and a push `sizeof` would all
agree on 8 where the truth is 1.

## What this changes about the lane

The stop pointed at "aggregate value semantics in the native backend" — a keystone redesign
(deep copy for aggregate fields, a layout-sized stride the array-literal store and index load must
adopt). That work is real and still ahead, but it is **not** what blocks the self-build today.
The first degrau of 0.3.1.0 is narrower and nameable: **`byte` has no machine class in the native
backend's LIR mapping.**

## Next steps, in order

1. Give `Byte` its arm in `ltype_of` (a one-octet integer class) and in `is_register_value_type`
   (`true`). Check `Char` for the same gap while there.
2. Confirm the three stride consumers agree on 1 for `[]byte`: the array-literal store, the index
   load, and the push `sizeof` argument. A guard that stops honestly is better than three
   consumers that disagree silently.
3. Re-run the measuring loop. Expect a NEW stop — `f64` already shows `B1-fp` waiting behind this
   one. Each stop is a degrau; record it here rather than widening the fix to meet it.

## Degrau 3 — `&&` and `||` have no lowering at all

```
teko: .: native backend N1: integer operator not yet lowered (N2)  [in `teko::backend::needs_lr_save`]
```

The named function is two lines: `func_any_call(f) && func_any_ret(f)`. The operator that stops is
`&&`.

### The minimal probe — 10ms instead of 3 minutes

`src/probe.tks`, with the virtual `src/main.tks` being just `exit(probe())`:

```teko
pub fn probe() -> i32 {
    let a = true
    let b = false
    if a && b { return 1 }
    0
}
```

`TEKO_BACKEND=native <gen1b>/teko . -o out --no-verify --release` reproduces the message verbatim,
with `[in `probe::probe`]`.

### The cause

`src/lir/lower.tks:829` — `lower_expr` sends EVERY `TBinary` to `lower_binary`, which lowers both
operands eagerly and then asks `lbinop_of` for an opcode. `lbinop_of` (`lower.tks:411`) splits on
the RESULT's `PrimKind`: float family, else integer family. `&&`/`||` are typed `Bool`
(`checker/typer.tks:745`, `type_logical_binop`), `Bool` is not a float kind, so a LOGICAL operator
is routed into `lbinop_int` (`lower.tks:441`) and dies in its `_ =>` at `lower.tks:453`.

Same shape as degrau 1 and 2 — a `_ =>` swallowing a case the rest of the compiler understands —
but the fix is NOT a new arm in that match. `&&`/`||` must SHORT-CIRCUIT: `lbinop_int` returning
`IAnd`/`IOr` would evaluate the right operand unconditionally and miscompile every
`p != null && p.field` guard in the compiler's own source. The lowering is control flow, and the
LIR already has every piece it needs — `lower_coalesce` (`lower.tks:3793`) is the exact template:
branch, two arms, a merge block whose single block-arg is the value.

### Why the message misleads

It says "integer operator". `&&` is neither integer nor an arithmetic operator; it is named that
only because `bool` rides in the integer family of `lbinop_of`'s two-way split. It also says "not
yet lowered", which reads as a missing OPCODE, when what is missing is a control-flow shape.

### Degrau 3 — CLOSED

`lower_binary` (`src/lir/lower.tks`) now intercepts `&&`/`||` BEFORE lowering either operand and
sends them to `lower_logical`, built in `lower_coalesce`'s shape: branch on the left operand into
either a `rhs` block (which lowers the right operand) or a `short` block (which materializes the
deciding constant — 0 for `&&`, 1 for `||`), both jumping to a merge block whose single block-arg
IS the expression's value.

The right operand must NOT be lowered eagerly, which is why the interception sits above
`lower_binary`'s body and not inside `lbinop_int`'s match: returning `IAnd`/`IOr` there would have
been the one-line "missing arm" fix and it would have MISCOMPILED every `p != null && p.field`
guard in the compiler's own source. This degrau is where the "a missing arm behind a `_ =>`"
pattern of degrau 1 and 2 stops holding: the arm was missing, but the arm was not the fix.

Regression: `short_circuit_and_or`, a member of the `own_native` corpus channel
(`examples/regressions/own_native/`) — the full truth table plus two rows whose RIGHT operand is a
divide-by-zero, so an eager lowering traps instead of merely returning a wrong number. Corpus exit
42 on both the native and the C route. Root `teko test .`: 1026 unit tests ok, regression summary
byte-identical to the pre-fix compiler's.

## Degrau 4 — aggregate slice elements. AN ARCHITECTURE DECISION, NOT A DEGRAU. STOP HERE.

```
teko: .: native backend N1: a push whose element is an AGGREGATE (`struct`/`class`/variant/optional/
closure) needs slice elements held BY VALUE — this backend's aggregate value is the address of a
per-INSTRUCTION frame slot, so a push in a loop would store the same address every iteration (N2)
[in `teko::backend::wrap_plain_words`]
```

`wrap_plain_words` (`src/backend/encode_arm64.tks:1633`) is `acc = teko::list::push(acc,
plain_word(ws[i]))` inside a loop — `EncWord` is a struct. This is the SAME message the lane's
first measurement reported, but this time it is not misdiagnosing: degrau 1 removed the `byte`
false positive that was wearing it, and what is left underneath is the real thing.

### What was measured before stopping

The stop's own text says slice elements must be held BY VALUE, which reads as "the array-literal
store and the index load must be widened too". They do NOT need to be, and that changes the shape
of the decision. This probe PASSES natively today:

```teko
pub type Point = struct { x: i32; y: i32 }

pub fn probe() -> i32 {
    let ps = [Point { x = 1; y = 2 }, Point { x = 3; y = 4 }]
    if ps[0].x != 1 { return 1 }
    if ps[1].x != 3 { return 2 }
    if ps[1].y != 4 { return 3 }
    0
}
```

It passes because `[]Aggregate` is, today, a slice of ADDRESSES: `ltype_of` gives a struct
`LType::Ptr`, so `lower_array_lit` (`lower.tks:6285`) uses stride 8 and stores the element's
address, and `lower_index_slice` (`lower.tks:6271`) loads one 8-byte word back — an address, which
IS the aggregate's value in this backend. The model is SELF-CONSISTENT, and its three consumers
already agree on 8.

The single place it breaks is the one that stops: an `alloca` is one frame slot per INSTRUCTION,
not per EXECUTION, so `loop { out = push(out, T { … }) }` pushes the same address N times.

### The decision, stated as two options

1. **By-value elements.** `[]Aggregate` gets a layout-sized stride: the array-literal store
   memcpies, the index computes `base + i*size` and does NOT load, the push passes the item's
   address with `esz` = layout size. Every consumer changes together, including the ones not yet
   written (slice-of-slice, a `for x in xs` binding, an `xs[i] = …` store, an aggregate argument).
2. **Fresh storage per push.** Keep `[]Aggregate` as a slice of addresses — every consumer above
   stays untouched and the probe keeps passing — and make `push` copy the aggregate into a FRESH
   runtime allocation, storing THAT address. It fixes exactly the aliasing that stops, and it also
   fixes the value-semantics hole the address model has anyway (`let p = …; xs = push(xs, p);
   p.x = 9` currently mutates the pushed element). Its cost is an ownership/lifetime call on the
   allocation (arena/region), which is a runtime decision, not a lowering one.

Option 2 is much narrower and option 1 is what the stop's text presumes. Choosing between them is
an architecture call with a runtime-lifetime consequence, so this cargo STOPS here rather than
picking one alone. It is on the critical path and it is unavoidable: the compiler is written in
slices of structs (`[]EncWord`, `[]LInst`, `[]MInst`, `[]LFunc`, …), so nothing else in the native
self-build can be measured until it is decided.

### Degrau 4 — CLOSED for `struct`/`class`, by the owner's OPTION 2 (ruling 2026-07-28)

The owner ruled: **narrow option now, by-value model later, as its own lane.**

- The slice of ADDRESSES STAYS. No consumer changed — the array-literal store still writes with
  stride 8, the index load still reads one word back, and the two-`Point` literal probe above still
  passes natively.
- A push whose element is an aggregate now COPIES the aggregate into a FRESH per-EXECUTION
  allocation and pushes THAT address.
- The value-semantics hole in ASSIGNMENT (`let a = ps[0]` aliases instead of copying) is left OPEN
  ON PURPOSE. It is the next lane, not this degrau.

What landed (`src/lir/lower.tks`, `src/runtime/teko_rt.{c,h}`):

| piece | what it does |
|---|---|
| `push_box_bytes` | 0 for a register value; the element's registered layout size for a nominal aggregate; the honest stop otherwise |
| `box_push_item` | emits `tk_slice_elem_box(&item, size)` and pushes the RETURNED address |
| `tk_slice_elem_box` (runtime) | `tk_alloc(esz)` + `memcpy` — the copy is bump-allocated in the ROOT arena |

**Ownership/lifetime — the hard half.** Teko has automatic arena memory and no GC, so the question
was not "how to copy" but "who owns the copy". The answer is the one the push itself already uses:
`tk_slice_push` grows the buffer that will HOLD the address through `tk_alloc`, i.e. in the root
region. Boxing the element in the SAME region makes the element's lifetime equal to the lifetime of
every buffer that can name it — one `tk_arena_pop`/`tk_regions_free_all` reclaims both, and no
element can outlive or predecease its holder. There is no new lifetime rule to teach anyone.

**Why the runtime was touched.** The LIR has no memcpy op and no allocation op, and inventing an
unrolled load/store copy in the lowering would have put an ALLOCATION POLICY (which region? which
alignment?) into codegen, where the arena is invisible. One 4-line runtime entry keeps the policy
where the arena lives. It is the smallest possible addition and it is documented at both sites.

### The stop that SURVIVES, narrowed

`unsized_aggregate_push_stop` still fires — for an aggregate whose byte width the ELEMENT TYPE
ALONE does not fix:

- an **optional** (`T | null`) and a **variant**: their tag+payload wrapper is allocated to the
  ACTIVE case's payload width (`lower_null_union_construct`/`lower_variant_construct` size it per
  CONSTRUCTION), so a copy sized from the static type would over-read a narrow construction;
- a **closure**: its value is one address whose captured environment is a SECOND allocation a flat
  copy would alias rather than clone;
- a **nominal with no registered layout** (an interface).

A guard that stops honestly is better than one that passes in silence. Closing the variant/optional
arm means making the wrapper's size a whole-TYPE fact, which is a separate decision with its own
consumers — it is NOT pulled in here. (DEGRAU 6 made it one: the VARIANT arm is closed at
`variant_wrapper_bytes()`. The optional and the closure arms survive.)

### THE DIVERGENCE THIS INSTITUTIONALIZES — `NATIVE-AGG-SLICE-BY-ADDRESS`

Search for that token: it is in `lower_list_push`'s doc, in `push_box_bytes`'s doc, in
`tk_slice_elem_box`'s two runtime comments, and in the corpus `.tkr`'s Feature block.

**The native backend's `[]Aggregate` is a slice of ADDRESSES; the C route's is a slice of VALUES.**
Both give the same answer for construction, indexing, field reads and — now — for a push. They
DIVERGE on assignment out of a slice:

```teko
mut a = ps[0]
a.x = 99          // C route: `ps[0].x` stays; native: `ps[0].x` becomes 99 (a is an ALIAS)
```

That divergence is DELIBERATE and time-boxed: it is what makes degrau 4 a narrow change instead of
a keystone redesign. It must be watched until the by-value-element lane closes it. Nothing in the
regression corpus may claim either side of it — a scenario that pinned the aliasing behaviour would
make the divergence permanent by accident.

### The regression, designed to fail without the fix

`examples/regressions/own_native/` (the degrau-3 corpus channel), three members:

- `push_aggregate_in_loop` — four `BoxPt { x = i; y = i * 10 }` pushed ONE PER ITERATION, then every
  element checked against its own iteration's values plus an explicit `ps[0] != ps[3]` distinctness
  check. With the naive stand-in (push the `alloca` address as-is) every element reads back as the
  last one and the program exits 23; before degrau 4 it did not compile at all.
- `push_aggregate_copies_the_item` — mutating the source binding AFTER the push must not reach the
  element. This is the second hole the box closes, and the naive stand-in fails it too.
- `push_class_in_loop` — the `class` arm, boxed by the same registered layout width.

Both routes exit 42 (`TEKO_BACKEND=native` and `TEKO_BACKEND=c`), from ONE program.

## Degrau 5 — a `match`-VALUE is not a fat-pointer producer. CLOSED.

```
teko: .: native backend N1: fat-pointer receiver `match-expression` not yet lowered (N2)
[in `teko::backend::encode_one`]
```

Reached the moment degrau 4 cleared the aggregate push. Reproduced in 10ms:

```teko
pub fn probe() -> i32 {
    let n: i32 = 2
    let s = match n { 1 => "one"; _ => "three" }
    if s.len != 5 { return 1 }
    0
}
```

A MISSING ARM with the template already in the file — the degrau-1/2 shape, not the degrau-3 trap.
`lower_fat_expr` accepts a closed producer set (literal, array literal, bound local, struct field,
`if`-expression, direct call) and a match-value was not in it. `lower_match_fat` is
`lower_match_value`'s arm chain wearing `lower_if_fat`'s two-param merge: the subject lowers once,
each arm's tail goes through `lower_block_value_fat`, and the merge's FIRST two block-args are the
(ptr, len) pair with the reassigned scalars after it. The dead fall-through past the last arm test
carries a defensive pair whose halves each take `lfallback_const` of their OWN machine class (a bare
`0` for the length would wasm-encode i32-narrow and collide with the real edges).

`native_match_fat_known_stop` went red the day the gap closed, exactly as its own note asked. Its
positive claim was promoted into the `own_native` corpus (`fat_match_value`). The project itself
could NOT be promoted: one stop deeper its `speak_or` hits
`fat-pointer interface-dispatch result not yet lowered` — a different family (the call ABI, not the
producer set) — so it was renamed `native_iface_fat_known_stop` and pins THAT stop by name.

## Degrau 6 — a variant whose member is FAT. An architecture decision — RULED ON, and CLOSED.

```
teko: .: native backend N1: slice match pattern not yet lowered (N2) [in `teko::backend::encode_one`]
```

The named site is `match emit_epilogue(layout) { []u32 as w => w; error as e => return e }` — the
spelling the compiler's own source is written in, hundreds of times over.

### Reproduced in 10ms, and the C route compiles the same program

```teko
fn make(n: i32) -> []i32 | error {
    if n == 0 { return error { message = "no" } }
    let xs: []i32 = [1, 2, 3]
    return xs
}

pub fn probe() -> i32 {
    let r = make(1)
    match r {
        []i32 as xs => { if xs.len != 3 { return 1 } }
        error => { return 2 }
    }
    0
}
```

### Why it is NOT the missing arm it looks like

`lower_bind_pattern_test` refuses `bp.is_slice` in one line, which reads like degrau 1 and 2. It is
not. Measure the CONSTRUCTION side and the gap is upstream of the pattern:

- `lower_variant_construct` allocates the uniform wrapper `{ i32 tag; payload }` of
  `8 + ltype_size(pty)` bytes and `store_variant_payload` stores ONE word of class `pty` at offset 8.
  For a `str`/`[]T` member `ltype_of` answers `Ptr`, so **the LENGTH is dropped at construction** —
  the probe's `make` lowers today and already builds a lossy wrapper.
- `bind_payload_at8` binds ONE scalar VReg through `ctx_bind`, not `lenv_bind_fat`.

So giving `is_slice` its arm would bind an `xs` whose `.len` reads whatever sits past the pointer.
That is degrau 3's trap wearing degrau 1's clothes: the arm is missing, and the arm is not the fix.

### The decision this needed


**What is a variant/optional wrapper's SHAPE when a member is fat?** The candidate is a uniform
`{ i32 tag; ptr; len }` (24 bytes, 8-aligned) that every member pays for, which changes together:
the construction store, the payload bind (scalar vs fat), the return path, the `Optional` twin, and
every existing tag test's offsets.

It is not separable from degrau 4's open half, and that is the strongest reason to decide them
together: `unsized_aggregate_push_stop` still refuses to box an optional/variant element precisely
because the wrapper is sized PER CONSTRUCTION rather than per type. A uniform wrapper closes that
stop as a side effect; a per-construction one keeps it open forever.

It is on the critical path — the compiler's own error handling is written in `T | error` unions with
fat `T`s — and nothing further in the native self-build can be measured until it is decided.

### Degrau 6 — CLOSED by the owner's ruling of 2026-07-28: a UNIFORM 24-byte wrapper

**`{ i32 tag@0; ptr@8; len@16 }`, 8-aligned, for EVERY variant/optional and EVERY case.**

One shape, one set of offsets, no special cases. The owner chose it knowing it wastes 8 bytes on
every case that has no fat member, and knowing the compiler is full of them: in a compiler that is
cheap, and uniformity is the opposite of what has bitten this lane four times — always one case
falling into a `_ =>`.

**Rejected explicitly, so they are not re-proposed:**

- *Box the fat payload behind one word.* It would deepen the by-address aggregate model that is
  already marked for demolition (`NATIVE-AGG-SLICE-BY-ADDRESS`).
- *Size the wrapper per member.* A variable payload offset is exactly the extra surface on which a
  case can fall through a `_ =>` again.

**Accepted cost:** 8 bytes per variant value with no fat member.

### The consumers that had to move — the list that keeps the next one from forgetting

The wrapper is written in ONE place and read in FOUR, and the width is asked for in THREE more.
Every one of them is named here because a forgotten consumer is a silent miscompilation:

| consumer | file | what changed |
|---|---|---|
| `variant_wrapper_bytes` / `variant_payload_offset` / `variant_payload_len_offset` / `variant_wrapper_align` | `src/lir/lower.tks` | NEW. The shape is now four named facts instead of arithmetic spread over two constructors |
| `lower_variant_construct` | `src/lir/lower.tks` | allocates the uniform width/alignment; passes the payload's TYPE (not its `LType`) down |
| `lower_null_union_construct` | `src/lir/lower.tks` | same, for the null-bearing twin |
| `store_variant_payload` | `src/lir/lower.tks` | splits on `is_fat_type` into `store_fat_variant_payload` (ptr@8 + len@16, through `lower_fat_expr`) and `store_scalar_variant_payload` (one word @8) |
| `bind_case_payload` (was `bind_payload_at8`) | `src/lir/lower.tks` | splits the same way: `bind_fat_case_payload` loads BOTH halves and `ctx_bind_fat`s them; `bind_scalar_case_payload` keeps the single-word load |
| `bind_null_union_payload` | `src/lir/lower.tks` | passes the payload TYPE through instead of collapsing it to an `LType` |

### The order was the lesson of degrau 3

The construction learned to keep the length FIRST; the pattern got its arm SECOND. Giving
`bp.is_slice` its arm alone would have bound an `xs` whose `.len` is whatever sits past the pointer
— it would have compiled and miscompiled in silence.

**Measured, not assumed.** Three probes against the CURRENT-source compiler, before any change:

| probe | stop |
|---|---|
| `[]i64 \| error` + `[]i64 as xs` | `native backend N1: slice match pattern not yet lowered (N2)` |
| `str \| error` + `str as s` (a NAME-resolved case, no slice pattern at all) | ``native backend N1: `s` is not a fat-pointer local (internal)`` |
| `str \| null` + `str as s` (the fixed-index null-union bind) | the same |

The second and third are the proof the gap was in the CONSTRUCTION: they never touch the slice

### Degrau 7 — string equality. A MISSING ARM, and CLOSED (same cargo, own commit)

```
teko: .: native backend N1: `str` has no single PrimKind, asked by the comparison chain (N2)
[in `teko::backend::name_in_symbols`]
```

Reached the moment degrau 6 cleared the slice pattern. The named site is
`syms[i].name == name` — a `str == str`. Reproduced in 10ms with three literals.

`lower_compare` sends every operand through `prim_kind_of`, which answers "which SINGLE machine
kind is this?". A `str` is two words and has none, so the chain stopped. `lower_str_compare` now
intercepts a `str`-typed subject BEFORE the chain and calls the runtime's own `tk_str_eq` with the
two ABI-flattened pairs `(a.ptr, a.len, b.ptr, b.len)` — the same flattening every fat argument
already gets, and the same by-symbol runtime use `tk_slice_push`/`tk_alloc` are. **No runtime entry
was added**; `tk_str_eq` has always been there.

TWO details that are the whole difference between an answer and a coin flip:

1. **The C `bool` return only defines its LOW BYTE.** `tk_str_eq`'s body is `memcmp(...) == 0`, so
   the bits above that byte carry the comparison's leftovers. The first build tested the whole
   register against zero and reported `"abc" == "abd"` as TRUE. The result is now narrowed through
   `narrow_extern_return`'s 8-bit unsigned shape first — the very hole
   `extern_return_narrow_of_prim` documents and leaves open for declared externs.
2. `!=` is the same call with the opposite predicate (`str_eq_predicate`), and an ORDERED `str`
   comparison (`<`, `>=`, …) keeps its own named honest stop — it would need `tk_str_cmp` and a
   lexicographic contract this backend has never claimed.

Regression: `str_equality`, a member of the `own_native` corpus — same-length-but-different, a
last-byte-only difference, two equal strings in DIFFERENT buffers (a pointer comparison would call
them different), and the empty pair (whose pointer is null). 42 on the native route and on the C
route.

### Degrau 8 — the next stop, reached in 22s, AND a silent miscompilation found beside it

```
teko: .: native backend N1: a push whose element is the nominal type `teko::backend::MInst`,
which has no registered layout … [in `teko::backend::push_minst_block`]
```

`MInst` is a DECLARED variant (`pub type MInst = variant MAlu | MAluImm | …`), so it reaches
`push_box_bytes` as a `checker::Named`, not as the inline `checker::Variant` degrau 6 closed. Whether
that is one more arm (look the name up in the variant table and answer `variant_wrapper_bytes()`) or
an architecture call depends on a question NOT yet answered: **is a declared-variant value the same
24-byte wrapper an inline union's value is?** Do not assume it — measure it, because the probe below
says something is already wrong there.

**MEASURED AND NOT FIXED HERE, CLOSED IN ITS OWN CARGO (`cargo/0.3.1.0-match-arm`, see the section
after this degrau):** a `match` over a DECLARED variant picks the WRONG ARM natively, silently.

```teko
type Circle = struct { r: i64 }
type Square = struct { s: i64 }
type Shape = variant Circle | Square

fn pick(n: i64) -> Shape { if n == 0 { return Circle { r = 7 } }; Square { s = 9 } }

pub fn probe() -> i32 {
    match pick(1) { Circle => { return 3 }; Square as s => { if s.s != 9 { return 4 } } }
    0
}
```

Native exits **3** (the `Square` value took the `Circle` arm); the C route exits 0. It exits 3 with
the PRE-degrau-6 compiler too, so it is not the wrapper's widening — a bind pattern over a `Named`
subject that is not a registered enum falls into "always matches", so the FIRST arm always wins.
That is this lane's disease in its purest form: not a stop, a silent wrong answer.

### An architecture hazard MEASURED here, not introduced here — the returned wrapper dangles

A variant wrapper is an `alloca`, i.e. a frame slot of the function that CONSTRUCTS it. A function
that RETURNS `T | error` therefore returns the address of its own dead frame, and the caller reads
tag/payload out of it. It survives the common shape (`match f(x) { … }` reads it before anything
else can write there) and it is measurably WRONG when a deep call intervenes:

```teko
let r = make(4)          // `-> []i64 | error`, or `-> Pt | error`
if noise(60) == 999999 { return 9 }   // 60 nested frames
match r { … }            // reads a clobbered wrapper
```

Measured with the STRUCT-payload version of that probe: the pre-degrau-6 compiler returns 0 and the
post-degrau-6 compiler returns 1. **Both are dangling; only the luck of the frame layout changed.**
The same probe with the wrapper built and matched in ONE frame passes either way. This is the
degrau-4 family (`NATIVE-AGG-SLICE-BY-ADDRESS`: an aggregate's value is the address of a frame
slot).

**RECLASSIFIED by the owner, 2026-07-28 — this is a BUG, not a decision.** It was recorded above as
an allocation-policy question awaiting a ruling. The ruling is that there is no question:

> *"A fuga, ocorreu por má implementação em native, em C funciona. Posse, já funciona hoje em C"*

The C route returns the same shape correctly. So there is no design to settle and nobody to wait
for — there is a native defect with a working reference implementation beside it. Whoever takes
this reads how the C route owns the wrapper and makes the native route agree.

### THE ORACLE RULE — general, and it outranks any single finding

**While the C route exists, any BEHAVIOUR divergence between native and C is a native bug until
proven otherwise. It is not an architecture question.** The C route is the reference implementation.

An architecture decision is warranted only when the two routes AGREE and are both wrong, or when the
construct has no C counterpart at all.

The rule was already doing the work twice today before it had a name — the declared-variant
miscompilation below (native 3, C 0) and this dangling wrapper. Naming it stops the next agent from
halting to request a ruling when reading the C route would have answered it.

**Measured exception, which is why the rule says "until proven otherwise" and not "always":** a
declared variant with a `null` member (`type M = variant Box | null`) makes the C route fail with
`codegen: cyclic value-type dependency`, while the native route — after the declared-variant fix —
executes it correctly. The oracle is a strong prior, not scripture. When the two disagree, establish
which one is right before assuming.

### A CAUSA — e são DUAS metades, não uma

`checker::resolve_named` (`src/checker/resolve.tks:775`, arm `parser::TypeDecl`) mantém um tipo de
utilizador NOMINAL: `type Shape = variant Circle | Square` chega ao backend como
`checker::Named{"ns::Shape"}`, NUNCA como o `checker::Variant` que uma união INLINE `A | B` traz. E
todo o protocolo de união do backend casava em `checker::Variant`:

| metade | sítio (antes) | o que fazia com um `Named` |
|---|---|---|
| CONSTRUÇÃO | `lower_value_into_type` (`src/lir/lower.tks:2805`) | `_ => lower_expr` — **nenhum invólucro tag+payload era construído** |
| TESTE | `lower_named_bind_pattern_test` (`src/lir/lower.tks:4896`, `null => PatternTest{always=true}`) | "casa sempre" → **o PRIMEIRO braço ganha todos os sujeitos** |

Os dois erros CANCELAM-SE no braço 1: o bind do valor inteiro lê o payload não-embrulhado no offset
0, que é exactamente o que o `Circle` tem lá. Em qualquer outro braço, resposta errada e calada.

A hipótese registada pelo agente anterior ("um bind pattern sobre `Named` cai em casa-sempre") estava
CERTA mas era META-DE: corrigir só o teste teria trocado uma resposta errada por outra (o `tag@0`
lido de um `Circle` não-embrulhado é `7`, que não casa com braço nenhum).

### A CORREÇÃO — uma função, três sítios, uma tabela

`expand_named_variant(t, ctx.variants)` (`src/lir/lower.tks`) devolve a união que o `Named` declara.
Aplicada nos TRÊS pontos onde um tipo entra numa decisão de união — o sujeito do `match`
(`lower_match_subject`), o tipo DECLARADO da colocação e o tipo do VALOR colocado
(`lower_value_into_type` / `lower_value_into_null_union` / `lower_value_into_variant`) — para que
construção e teste leiam a MESMA lista de membros, na mesma ordem, da mesma tabela.

A tabela (`collect_variant_defs`, `src/lir/lower_const.tks`) expande cada corpo pelo resolvedor DO
CHECKER (`checker::resolve_type`, a mesma chamada que `checker::expand_variant` faz). **A armadilha
que custou um ciclo:** `checker::type_table_of` chaveia cada entrada pelo nome CANÓNICO (`p::Circle`)
com namespace vazio, e a regra R3 do resolvedor procura `entry.name == <bare> && entry.namespace ==
ref_ns` — contra essa tabela, TODOS os membros falham a resolver e o corpo cai num recurso nominal
sem qualificação. `declared_type_table` volta a partir o nome canónico em (bare, namespace), que é
como o resolvedor lê uma tabela; só assim os membros saem com o nome canónico que
`variant_member_type_matches` compara EXACTAMENTE (comparar por último segmento seria trocar um
silêncio por outro: dois tipos homónimos em namespaces diferentes deixariam de ser casos distintos).

A tabela SUBSTITUI a tabela só-de-nomes que o serializador de consts usava (`find_variant_info` →
`find_variant_def`): a etiqueta que uma imagem em rodata carrega e a etiqueta que um braço compara

## A alavanca foi virada — as 4 pernas Linux geram NATIVE, e o vermelho é a medição

**Ruling do dono, 2026-07-28 (literal):**

> "Só tem uma falha, gen2 e gen3 estão emitindo C e não deveriam, reabilite o check de emissão
> (somente nas pernas Linux), verá que não passará nada."

E, no mesmo dia:

> "como estamos trabalhando com foco em native, não devem existir novas emissões em C, a ideia é
> que gen1 aprenda a compilar native sem emitir C."

### Onde a alavanca ficou, e como o escopo é garantido

| ficheiro | o que mudou |
|---|---|
| `scripts/ci_producer_matrix.sh` | cada perna ganhou o campo `fixpoint_backend`. `native` nas quatro Linux (`linux-x86_64-glibc`, `linux-x86_64-musl`, `linux-arm64-glibc`, `linux-arm64-musl`), `c` em `windows-x86_64` e `macos-arm64`. |
| `.github/workflows/pr.yml` | o passo do fixpoint passa `TEKO_FIXPOINT_BACKEND: ${{ matrix.fixpoint_backend }}` — no PASSO, nunca no job nem no workflow. |
| `scripts/fixpoint_gate.sh` | `FIXPOINT_BACKEND="${TEKO_FIXPOINT_BACKEND:-c}"`, lido UMA vez e usado só dentro de `build_gen`, ou seja gen2 e gen3. A escada e o gen1 não são tocados (ruling de 2026-07-27: *"ele não pode nem deve avaliar a escada e nem a gen1, apenas gen2 e 3"*). |

**Por que um campo da matriz e não um `if:` no passo:** a tabela de pernas é consumida por `pr.yml`
E por `nightly.yml` a partir de UMA definição. Um estágio declarado como campo não pode ser
declarado num workflow e esquecido no outro; um predicado `endsWith(matrix.producer, 'linux-…')`
seria um sítio onde a sétima perna se perde.

**O `nightly.yml` não corre o fixpoint, e isso é DESENHO, não esquecimento.** Ruling do dono,
2026-07-28, literal:

> "Nightly não tem que correr fixpoint mesmo, não é pra isso"

Fica registado porque a ausência tem cara de lacuna e já foi levantada como tal uma vez. O nightly
tem outro propósito: prova a propriedade ENTRE execuções e ENTRE máquinas (*mesma árvore + mesmo
seed + mesma toolchain ⇒ mesmos bytes*), comparando o que cunha contra os assets do run de PR que
já portou o commit — o job `reproducibility`, "nightly === gen1 of the gated PR". O fixpoint prova
`gen2 == gen3` DENTRO de uma execução, e quem o corre é o `artifact` do `pr.yml`. São duas
perguntas diferentes; o nightly responde à sua. **Não acrescentar o fixpoint ao nightly.**

O `nightly.yml` lê a mesma tabela de pernas (`ci_producer_matrix.sh full`, no seu job `plan`), por
isso o campo `fixpoint_backend` viaja com ela; simplesmente não é consumido ali, e não é para ser.

O default do gate continua `c`: quem não nomeia backend recebe a rota que sempre funcionou.

### O check de emissão — JÁ EXISTIA, e estava desarmado por ruling datado

Não foi escrito do zero. Vivia em `scripts/fixpoint_gate.sh` como
`ZERO_C_ENFORCED="${TEKO_FIXPOINT_ZERO_C:-0}"` — REPORTA e não falha — desarmado em 2026-07-27
(*"pode remover por hora a validação de no-c para este caso"*), num mundo em que TODAS as pernas
construíam gen2/gen3 pela rota C de propósito. Nesse mundo, falhar por emissão de C seria pintar
de vermelho todas as corridas por fazerem exactamente o que a versão pedia.

(Existe também `scripts/no_emitted_c.sh`, o ratchet do `teko test`. NÃO foi ligado aqui, pela razão
que o próprio cabeçalho do gate dá: varre a worktree inteira e não sabe dizer de QUEM é a emissão
que encontrou.)

**O que mudou e como foi rearmado:** o armar é agora DERIVADO do backend, não configurado ao lado
dele — `zero_c_enforced_default()` devolve 1 se as gerações sob teste foram construídas com
`native`, 0 se foram pela rota C. Uma geração NATIVE que emite C é um defeito em qualquer versão.
Consequência: não existe segundo botão para esquecer, e nenhuma perna futura pode migrar para
nativo mantendo o check calado. `TEKO_FIXPOINT_ZERO_C` continua a sobrepor-se nos dois sentidos —
é para o vagão de 0.3.1.4, que arma o check nas pernas que ainda estiverem em C.

**O que o check verifica, exactamente:**

1. Todos os `.c` dentro do directório `-o` daquela geração (não só `teko.c` — QUALQUER `.c`).
2. O delta de um `find` sobre a árvore do projecto tirado ANTES e DEPOIS de cada build
   (`scan_project_c`), o que apanha um `.c` escrito ao lado dos fontes em vez de no `-o`.
3. Falha ALTO e NOMEIA cada ficheiro encontrado, com caminho absoluto, por geração
   (`report_emission`). Nada é excluído: uma allow-list é como um check armado apodrece até virar
   carimbo.

**Parametrizado por geração, de propósito.** `ZERO_C_GENERATIONS="$LEFT $RIGHT"` (hoje
`gen2 gen3`), e `record_emission` / `report_emission` / `emission_count` recebem um NOME de
geração. O destino do dono tem o gen1 também a não emitir C; nesse dia, estender é editar UM token
para `"gen1 $LEFT $RIGHT"`. A observação do gen1 já é registada por `stage_gen1_c`
(`$W/gen1.emitted-c{,-list}`) mesmo sem ninguém a ler. Hoje o gen1 NÃO é julgado, e isso não é
esquecimento: o ruling de 2026-07-27 proíbe-o.

**A colheita do `teko.c` do gen1 é caminho de DEGRAU, não caminho normal.** No caminho normal
ninguém emite C — nem gen1. Enquanto o gen1 não aprender a construir nativo, a sua emissão é o que
sustenta `bootstrap/teko.c`, e `bootstrap/teko.c` só entra em uso mediante declaração
(`bootstrap/DEGRAU`, ruling de 2026-07-28: *"só podemos usar teko.c se e somente se identificarmos
degrau"*). Corolário operacional: **nenhuma correcção pode passar por acrescentar emissão de C.**
Uma parada cuja saída fácil seja "emite C aqui" regista-se e reporta-se; não se implementa.

### O vermelho é o produto — MEDIDO EM RUNNER REAL, nas quatro pernas

As quatro pernas Linux ficaram vermelhas, e é isso que foi pedido (*"verá que não passará nada"*).
Não é previsão: é o run do vagão sobre `cc83f91`. As quatro param no **build do gen2**, com a
mensagem IDÊNTICA e no MESMO endereço N1:

```
teko: .: native backend N1: slice match pattern not yet lowered (N2)
  [in `teko::backend::encode_one`]
VERDICT: FAILED — gen1 does not build the source it came from
```

`linux-x86_64-glibc`, `linux-x86_64-musl`, `linux-arm64-glibc`, `linux-arm64-musl` — sem
divergência entre libc nem entre arquitecturas. macOS e Windows verdes na rota C, como o
sequenciamento por plataforma manda. É o **degrau 6** (o invólucro gordo de variante).

**O que o run validou além do endereço**, e que a medição local não alcançava: a alavanca apanha
só as quatro pernas Linux; o `bootstrap/teko.c` está presente mas é IGNORADO por não haver
declaração (`provenance = normal — release -> gen0 -> gen1`, exactamente a cadeia do dono); e o C
do gen1 foi encenado (10,17 MB).

**O check de emissão não chegou a correr, e esse é o comportamento certo:** sem gen2 não há
geração para examinar, e o gate falha antes, no build. Enquanto houver um degrau aberto, a alavanca
mede a distância até ele — a emissão de C só se torna a medição VISÍVEL quando a cadeia chegar ao
gen3.

**Registo anterior, corrigido e não apagado:** a primeira medição desta secção (local, sobre
`43cabb5`) apontava o degrau 4, `a push whose element is an AGGREGATE … [in
`teko::backend::wrap_plain_words`]`. Estava certa para aquele tip e ficou obsoleta em horas: os
degraus 4 e 5 fecharam entretanto. A lição é sobre o método, não sobre o endereço — **uma previsão
tirada de uma máquina e de um tip envelhece mais depressa do que se escreve**, e só o run das
quatro pernas sobre o tip corrente é medição.

**E a ausência de divergência é ela própria uma prova.** Se estas fossem quatro falhas ortogonais
da EMISSÃO, as quatro mensagens teriam divergido — libc e arquitectura diferentes, endereços
diferentes. Não divergiram, porque é a mesma baixa PARTILHADA medida quatro vezes. É o resultado
que o sequenciamento por largura previa (ver `0.3.1-plano-sequenciado-por-plataforma.md`): quatro
pernas de uma só baixa, e por isso quatro pernas ao preço de uma.

### Como se vira de volta (para não haver arqueologia)

Uma palavra por perna, em `scripts/ci_producer_matrix.sh`: trocar `"fixpoint_backend":"native"` por
`"fixpoint_backend":"c"` na linha daquela perna. Mais nada se mexe — o check de emissão é DERIVADO
desse campo, portanto desarma sozinho. Nos dois sentidos.

O que NÃO se deve fazer para tirar o vermelho: `continue-on-error`, transformar o check em aviso,
estreitar o critério, excluir ficheiros do varrimento, ou pôr `TEKO_FIXPOINT_SOFT=1`. O ruling de
2026-07-27 já cobriu essa família: *"se ele diz que falhou, deveria ter saído com exit(1) para
sinalizar vermelha a lane"* e *"se esse vagão fechar verde é pura mentira"*.

para validação, pode criar ymls personalizados para push para validação."* Instrumento descartável:
o que lá está e não se destina ao vagão não entra na `cargo/`.

existia para dar — as quatro pernas, mesma paragem, sem divergência por libc ou arquitectura — e
hoje ela só repetiria o que já se sabe. Volta a servir quando o **degrau 6** fechar e a pergunta
voltar a ser útil: *arm64 ou musl escondem uma paragem que o x86_64 não mostra?*
