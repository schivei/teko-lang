# Plano de Sequenciamento por Plataforma — 0.3.1 (ruling do dono, 2026-07-28)

## A Cadeia de Geração e o Veredito do Fixpoint

**A cadeia (ruling do dono, 2026-07-28):**

```
release 0.3.0.31 --TEKO_BACKEND=c--> gen0 --TEKO_BACKEND=c--> gen1 (emits teko.c)
                 --native--> gen2 --native--> gen3        ASSERT gen2 == gen3
```

**O que muda na comparação:** o veredito do fixpoint **fica fixo em `gen2 == gen3`**, nunca mudando para `gen1 == gen2`. Citação literal do dono:

> "gen1 aqui nunca será igual gen2 pq gen1 ainda precisa depender de ser emitido com um seed que emite C, mas a gen1 deve aprender a não emitir C, por isso o fixpoint não muda, o que muda é que, para gerar gen1 TEKO_BACKEND=C, para gen2 e 3, native (sem a variável de ambiente)."

**Por que gen1 não entra na comparação:** gen1 é C por construção (última geração antes de colher `teko.c`), gen2 é nativo. Dois geradores diferentes (`cc` vs backend próprio do Teko) não podem concordar byte-por-byte, pelos mesmos motivos que o mesmo `teko.c` compilado com `cc` e com `musl-gcc` emite dois artefatos diferentes. O fixpoint começa onde o compilador passa a se alimentar do seu próprio output — isso é gen2.

## A Inversão do `teko.c`: Entrada → Saída

**Até agora:** `bootstrap/teko.c` era UMA ENTRADA: commitado porque a release publicada não podia construir o tip (rung -1 da escada).

**A partir de agora:** `teko.c` é UMA SAÍDA, versionada após uma corrida verde:
- Colhido **do gen1** (a última geração na rota C).
- Armazenado após o verde, não antes.
- Quando gen2 e gen3 forem nativos em todas as pernas, `gen3.c` deixa de existir.

**A regra do portão (ruling do dono, 2026-07-28):**

> "só podemos usar teko.c se e somente se identificarmos degrau."

**O critério mudou:** deixou de perguntar "o ficheiro `bootstrap/teko.c` existe?" e passou a perguntar "há uma declaração `bootstrap/DEGRAU`?" — uma afirmação humana de que alguém entendeu por que a release publicada não chega aqui. A presença do C é dado; a declaração é a ponte. Sem declaração, não há ponte — o C fica aí, mas não entra em uso.

## Sequenciamento por Plataforma

**A fórmula de versão fica intacta**; o bump continua incremental.

**A geração é decidida POR PERNA, não globalmente:** cada plataforma flipa para nativo quando o seu backend nativo conseguir compilar o compilador. A alavanca é `TEKO_FIXPOINT_BACKEND` em `scripts/fixpoint_gate.sh` (linha 191, dentro da função `build_gen`, terceira linha: `bg_backend="${TEKO_FIXPOINT_BACKEND:-c}"`), com escopo **SÓ em `build_gen` — ou seja gen2 e gen3, nunca a escada, nunca o gen1.**

**Ruling do dono (2026-07-27, repetido porque o implementador re-derivou em vez de aplicar):**

> "ele não pode nem deve avaliar a escada e nem a gen1, apenas gen2 e 3"

**O plano de migração, por versão:**

- **0.3.1.0:** as 4 pernas Linux (`x86_64-glibc`, `x86_64-musl`, `arm64-glibc`, `arm64-musl`) passam a gerar NATIVE.
- **0.3.1.1 até 0.3.1.4:** macOS, Windows e wasm continuam na rota C.
- **Depois de 0.3.1.4:** o backend C é aposentado; cada perna que migrou para nativo já não o usa, as restantes migram ou são pausadas.

**Discrepância encontrada:** `docs/design/star-ref-and-ffi-0.3.1.md` (linhas 45–47) situa o "C backend DEAD" no `.32` (historicamente 0.3.0.32, mas o contexto sugere versão de design anterior). Sob o plano sequenciado de 2026-07-28, o backend C vive até **0.3.1.4** inclusive, e é aposentado depois (versão específica por plataforma — uma que migrou para nativo não o usa mais, as outras migram ou pausam). Este documento de memória sobrepõe o timeline antigo.

## Por que Linux é Sequenciado Primeiro — é Largura, não Facilidade (ruling 2026-07-28)

Ruling do dono, literal (2026-07-28):

> "Tirando a emissão nativa (bytes gerados), o código é o mesmo para todos, Windows, Mac e wasm também, mas vale ressaltar que eles podem ter muita coisa que não vão funcionar, atacar o Linux agora é só pela quantidade de pernas, não por dificuldade."

**A razão:** não é que Linux seja mais fácil. É que as quatro pernas Linux (`x86_64-glibc`, `x86_64-musl`, `arm64-glibc`, `arm64-musl`) medem a **mesma baixa partilhada** em quatro combinações diferentes — a maior cobertura por unidade de esforço.

**O que é partilhado e o que é não:** a baixa de LIR (`src/lir/lower.tks`) é partilhada entre TODAS as plataformas. Só a emissão de bytes é por plataforma — a seleção de instruções (`isel x86-64`, `isel arm64`, `isel wasm`), os escritores de objeto (ELF, PE, Mach-O), e as variantes específicas como `B1-fp` (floats em x86-64), `B1-args` (argumentos em pilha no Windows). **Portanto os degraus 1 a 6 já beneficiam macOS, Windows e wasm**, sem ninguém lhes ter tocado: o `byte` sem classe de máquina, o caso de variante por palavra-chave, o `&&`/`||` ansioso, o `push` de agregado, o `match`-gordo e o invólucro de variante são todos correções em código partilhado que qualquer plataforma que chegar aqui receberá.

**O que sobra para as outras plataformas — pode ser muito:** macOS e Windows têm o seu próprio trabalho de emissão. Citação do dono: *"eles podem ter muita coisa que não vão funcionar"*. Esse trabalho é toda a metade de emissão: a seleção de instruções para `x86-64` (inclusive `B1-fp` para floats), o `B1-args` (argumentos em pilha no Windows), o `TimeDateStamp` do PE (que matou o fixpoint do Windows na 0.3.0.31), e os escritores de objeto. Tudo ortogonal à baixa partilhada.

### Evidência Empírica — as Quatro Paragens Idênticas (cc83f91, 2026-07-28)

No run do commit cc83f91 com a alavanca virada, as **quatro** pernas Linux pararam com mensagem **IDÊNTICA**:

```
native backend N1: slice match pattern not yet lowered (N2)  [in `teko::backend::encode_one`]
VERDICT: FAILED — gen1 does not build the source it came from
```

Se fossem quatro problemas independentes, as mensagens divergiriam — pois cada plataforma tem a sua emissão de bytes. Não divergiram — porque é a **mesma baixa partilhada, medida quatro vezes**. macOS e Windows ficaram verdes na rota C, o que confirma que o sequenciamento não contaminou as outras pernas. Detalhe desta paragem em `docs/memory/0.3.1.0-linux-native-first-stop.md#degrau-6`.

### A Ordem de Dificuldade das Plataformas — Por que NÃO foi Escolhida a Mais Fácil (ruling 2026-07-28)

Ruling do dono, literal (2026-07-28):

> "Se for falar de facilidade, diria: macOS->Linux->Windows->Wasm Browser->Wasm WASI"

**A ordem crescente de dificuldade é:** macOS (a mais fácil), Linux, Windows, Wasm Browser, Wasm WASI.

Isto **NÃO contradiz** o ruling anterior (*"atacar o Linux agora é só pela quantidade de pernas, não por dificuldade"*) — afia-o. **O projeto atacou a SEGUNDA mais fácil deliberadamente**, trocando um pouco de dificuldade por quatro vezes a largura:

- **macOS:** uma arquitetura (arm64), uma libc (system), Mach-O — **UMA perna só**. A baixa partilhada roda ali, mas mede-a uma única vez. Sem largura.
- **Linux:** a mesma baixa, mas duas arquiteturas (`x86_64`, `arm64`) × duas libc (`glibc`, `musl`), ELF — **QUATRO pernas**. A baixa partilhada mede-se quatro vezes, validando com muito maior confiança.

**A metade ortogonal — a emissão** — respira desta ordem. Todos os degraus 1 a 6 beneficiam todas as plataformas porque é código partilhado. A ordem crescente de dificuldade que se enumerou é a ordem da **metade de emissão**:

- **macOS:** Mach-O apenas. Trabalho de escrita de objeto, sem variantes de ABI ou arquitetura.
- **Linux:** ELF (idêntico para as 4 pernas), sem extras. O trabalho é só a isel (`isel x86_64`, `isel arm64`), que é duplicado mas simétrico.
- **Windows:** PE, o `TimeDateStamp` do PE (que matou o fixpoint do Windows no byte 137 na 0.3.0.31), e o `B1-args` (argumentos em pilha — Win64 tem 4 registos de argumento, System V tem 6). Documentado em `docs/memory/b1-args-stack-slot.md`.
- **Wasm Browser:** modelo de máquina diferente — sem registos, controlo de fluxo estruturado (stackifier de LIR para `block`/`loop`/`if`, sem `br_table`). A emissão é ortogonal à baixa de LIR; a baixa serve wasm também.
- **Wasm WASI:** tudo isso mais a superfície de syscalls e o runtime linking (via `wasm-ld`, o cc-as-linker analogue).

### Próxima Medição Planeada — Separação das Duas Metades

Quando o degrau 6 fechar e as quatro pernas Linux passarem, a próxima medição barata é **virar o macOS** — a mais fácil — numa branch `theory/**`, para separar as duas metades (baixa partilhada vs emissão por plataforma):

- **Se passar logo:** prova que o restante que falta é só emissão; a baixa partilhada foi resolvida por arrasto dos degraus 1-6.
- **Se parar:** o que a fizer parar é informação limpa, sem o ruído de ser difícil — sabe-se que macOS é a mais fácil, portanto o stop é um sinal forte de que é realmente importante.

Escolhe-se a mais fácil de propósito: maximiza a confiança em qualquer resultado. **Nada a fazer agora — é jogada seguinte após o degrau 6 fechar.**

## Os Degraus Já Fechados na Lane 0.3.1.0

Detalhes completos em `docs/memory/0.3.1.0-linux-native-first-stop.md` (o registo detalhado, não repetido aqui):

1. **Degrau 1 — `byte` sem classe de máquina:** `src/lir/lower.tks` faltavam braços em `ltype_of` e `is_register_value_type` para a variante `Byte`. O doc-comment do `is_register_value_type` já dizia "byte", mas o código discordava silenciosamente via `_ => false`. O portão acusava "push de agregado num loop"; na verdade era `byte` que não tinha classe de máquina (I8, como `bool`). Fechado.

2. **Degrau 2 — Caso de variante escrito por palavra-chave:** `src/lir/lower.tks::variant_member_named` reconhecia apenas casos nominais (`Named`), deixando cair casos escritos com tipo-palavra-chave (`u32`, `byte`, `str`, …) no `_ => false`. Resolvido com `checker::builtin_case_name`, a inversa da tabela `scope.builtin_type`. Fechado.

3. **Degrau 3 — `&&`/`||` como operadores inteiros:** `src/lir/lower.tks::lower_binary` passava `&&`/`||` direto para `lbinop_of`, que os roteava para `lbinop_int` (porque `bool` é da família inteira na divisão do split binário). Lá morriam no `_ =>` da linha 453. O portão dizia "operador inteiro não abaixado", o que é enganoso: `&&`/`||` não são operadores aritméticos, são controlo de fluxo e devem **curto-circuitar**. Resolvido com `lower_logical` construído na forma `lower_coalesce` (ramificação no operando esquerdo, dois braços para rhs/short, bloqueio de merge com o valor). A captura teve que estar **antes** de baixar qualquer operando, ou a alternativa (devolver `IAnd`/`IOr`) teria miscompilado todo o guarda `p != null && p.field` do próprio compilador. Fechado.

4. **(Em curso) Degrau 4 — `push` de agregado num loop:** o portão diz "slice elements must be held BY VALUE". O sondagem mostra que `[]Aggregate` hoje é uma slice de ENDEREÇOS (porque `ltype_of` dá a um struct `LType::Ptr`), e isso é auto-consistente — array-literal store usa stride 8, index load também. Só quebra numa linha: `loop { out = push(out, T { … }) }` porque `alloca` é um slot por INSTRUÇÃO, não por EXECUÇÃO, então a mesma morada é enfiada N vezes. **É uma decisão de arquitetura**, não um degrau: escolher entre (1) elemetos por valor (stride layout-sized, mudança em todos os consumidores, presentes e futuros) ou (2) nova armazenação por push (cópia para alocação fresca, model mais simples, mas chamada de lifetime no arena/região). A decisão está com o dono. Continua a medir.

## A Lição Transversal

Três dos quatro degraus (1, 2, 3) caíram no padrão **um braço engolido por um `_ =>`**, com o resto do compilador já a entender o caso:

- **Degrau 1:** o próprio doc-comment de `is_register_value_type` já dizia "`byte`"; o checker já aceitava `byte`; apenas o LIR o rejeitava silenciosamente.
- **Degrau 2:** o checker já aceitava `u32` como caso de variante; apenas o lowering o rejeitava.
- **Degrau 3:** parecia igual, com um braço que faltava… mas **não era igual.**

**Por que o degrau 3 é diferente e custa caro:** o braço existia (a forma `lower_coalesce` já estava lá, usada em múltiplos sítios). Devolver um novo opcode (`IAnd`/`IOr`) teria compilado e **miscompilado** todos os guardas `p != null && p.field` do compilador (e de qualquer programa). A primeira metade da lição ("um `_ =>` engole um caso") é fácil de ver. A segunda metade — que o braço pode existir mas estar ERRADO para este contexto — não se vê até a corrida: é aí que custa caro.

**Registe ambas as metades, não só a primeira.** Quando um stop aponta para uma família que o resto do compilador já entende, pergunte: é falta de braço, ou é um braço que existe mas está errado para este caso?
